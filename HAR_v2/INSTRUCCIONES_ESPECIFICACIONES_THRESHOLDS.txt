================================================================================
1. RESUMEN DEL SISTEMA
================================================================================

Programa de Human Activity Recognition (HAR) basado en REGLAS GEOMÉTRICAS
heurísticas sobre esqueletos 2D (8 keypoints de torso/brazos).

NO usa machine learning en esta versión.

Entrada típica:
  - poses_full.npy  →  shape (T, 8, 2), coordenadas normalizadas ~[0,1]
  - meta.json       →  fps del clip (y metadatos)
  - clip.mp4        →  vídeo del clip (solo para validación visual full)

Salida típica:
  - .txt con segmentos: ACTION | START | END | DURATION | CODE
  - ubicado en output/<clase>/<CLIP>/

Objetivo:
  Detectar estados corporales persistentes y acciones dinámicas (transiciones),
  con filtrado temporal anti-ruido, códigos de fiabilidad 0/1/2, y herramientas
  de validación visual in-situ.

3.2 Formato .npy
----------------
Aceptado por el cargador:
  (T, 8, 2)     frames × joints × (x, y)          ← principal
  (T, 8, 3)     se ignora z / score en el 3er canal
  (T, 2, 8, 2)  dos usuarios → se usa usuario 0

Coordenadas: normalizadas típicamente en [0, 1] respecto al frame del vídeo.
Convención de imagen: y_down = True (y crece hacia abajo, como OpenCV).

poses_full.npy:
  Puede contener NaN en frames sin detección válida.
  A menudo acompaña valid_mask.npy (bool, T).

poses.npy:
  Versión filtrada (solo frames válidos concatenados). El detector trabaja
  preferentemente con poses_full.npy + timestamps alineados al vídeo.

3.3 meta.json
-------------
Debe contener al menos:
  "fps": <float>

El programa busca meta.json subiendo desde el .npy (hasta 4 niveles).
Caso típico: .../CLIP/user_XXX/poses.npy → .../CLIP/meta.json

3.4 clip.mp4
------------
Usado solo por validate_realtime_full.py.
Se busca automáticamente en la carpeta del CLIP:
  clip.mp4, clip.avi, o <CLIP_NAME>.mp4

Si el número de frames del mp4 y del npy no coincide, se usa min(T_npy, T_mp4)
y se imprime un warning.

7. FORMATO DE SALIDA (.txt)
================================================================================

Cabecera:
  # ACTION SEGMENTATION RESULTS
  # source: <ruta_npy>
  # fps: <float>
  # columns: ACTION | START | END | DURATION | CODE
  # CODE: 0=green  1=yellow  2=red
  # num_frames=...
  # duration_s=...
  # num_segments=...
  # fps_source=...

Líneas de datos:
  ACTION | HH:MM:SS.mmm | HH:MM:SS.mmm | DURACION_SEG | CODE

Ejemplo:
  WRIST_NEAR_WAIST_LEFT | 00:00:02.019 | 00:00:03.312 | 1.293 | 0
  EXTEND_ARM_RIGHT      | 00:00:05.120 | 00:00:05.680 | 0.560 | 0
  PERSON_PROFILE_HEURISTIC | 00:00:01.000 | 00:00:08.000 | 7.000 | 1

Final obligatorio:
  # UNSUPPORTED WITH 2D KEYPOINTS
  ARM_FORWARD_DEPTH | CODE=2
  ARM_BACKWARD_DEPTH | CODE=2
  HAND_FRONT_BACK | CODE=2
  TORSO_ROTATION_3D_EXACT | CODE=2
  SHOULDER_ANGLE_3D | CODE=2
  WRIST_DEPTH | CODE=2

Timestamps:
  frame i → t = i / fps
  formato legible: HH:MM:SS.mmm

Solapamiento:
  Varias etiquetas pueden coexistir en el mismo intervalo (no es clasificación
  exclusiva por frame).

8. ARQUITECTURA INTERNA
================================================================================

Pipeline:
  .npy
    → PoseSequence (validación shape/FPS/keypoints)
    → FeatureExtractor (suavizado coords → geometría → derivadas)
    → StateDetector (histeresis sobre features → segmentos estado)
    → ActionDetector (FSM de transiciones → segmentos acción)
    → SegmentProcessor (merge gaps + duración mínima)
    → write_results_txt / UI

Clases principales:
  PoseSequence, FeatureExtractor, FeatureSet
  StateDetector, ActionDetector, ActionAnalysisPipeline
  SegmentProcessor, Segment, DetectionConfig


================================================================================
9. KEYPOINTS Y CONVENCIONES GEOMÉTRICAS
================================================================================

Mapping centralizado (har_pose/config.py → KEYPOINTS):
  0  left_shoulder
  1  right_shoulder
  2  left_elbow
  3  right_elbow
  4  left_wrist
  5  right_wrist
  6  left_hip
  7  right_hip

Origen: subset COCO upper-body [5,6,7,8,9,10,11,12] del extractor YOLO.

Centros:
  Sc = (left_shoulder + right_shoulder) / 2     # centro hombros
  Hc = (left_hip + right_hip) / 2               # centro cintura
  C  = α·Sc + (1-α)·Hc                          # pecho aproximado
       α = chest_alpha = 0.65

Escala corporal (normalización de distancias):
  scale = 0.55 · ancho_hombros + 0.45 · distancia(Sc, Hc)
  floor: min_body_scale = 1e-3

Ángulo de codo:
  θ = ángulo en el codo del triángulo hombro–codo–muñeca, grados [0,180]
  ~180° ≈ brazo extendido/recto

Alturas relativas (y_down=True):
  height = (ref_y - wrist_y) / scale
  positivo ⇒ muñeca más arriba que la referencia en la imagen

================================================================================
11. FILTRADO TEMPORAL
================================================================================

11.1 Suavizado
--------------
  method default: "savgol" (polyorder 2, window 5)
  alternativas: "mean", "median"
  Los NaN originales se conservan (no se inventan poses en frames inválidos).

11.2 Histeresis
---------------
  mode "above": entra si value > enter; sale si value < exit  (enter ≥ exit)
  mode "below": entra si value < enter; sale si value > exit  (enter ≤ exit)
  mode "abs_below": entra si |value| < enter; sale si |value| > exit

Evita flickering alrededor del umbral.

11.3 Duración mínima
--------------------
  Estados:  min_state_duration_s  = 0.20 s
  Acciones: min_action_duration_s = 0.12 s
  Segmentos más cortos se descartan.

11.4 Unión de gaps
------------------
  merge_gap_s = 0.12 s
  Si la misma etiqueta desaparece y reaparece en ≤ merge_gap_s, se fusionan.


================================================================================
12. ESTADOS VS ACCIONES (FSM)
================================================================================

ESTADO (persistente):
  Ej: ARM_EXTENDED_LEFT — el brazo permanece extendido un intervalo.
  Se detecta con histeresis sobre una feature.

ACCIÓN (transición dinámica):
  Ej: EXTEND_ARM_LEFT — paso de no-extendido a extendido con incremento
  significativo del ángulo de codo, derivada positiva y confirmación temporal.
  NO se etiqueta solo porque el vídeo ya empiece en el estado final.

FSMs conceptuales:
  FLEXED → EXTENDING → EXTENDED          (EXTEND_ARM_*)
  EXTENDED → RETRACTING → FLEXED         (RETRACT_ARM_*)
  FAR → APPROACHING → NEAR               (WRIST_TO_WAIST_*, WRIST_TO_CHEST_*)
  LOW → RAISING → ELEVATED               (RAISE_ARM_*)
  HIGH → LOWERING → DOWN                 (LOWER_ARM_*)

Parámetros FSM relevantes:
  extend_delta_elbow_deg, retract_delta_elbow_deg
  approach_delta_norm, min_action_speed_norm_s
  raise_delta_height, hands_sep_delta_norm, open_close_delta
  action_min_frames = 3

================================================================================
14. CÓDIGOS DE FIABILIDAD
================================================================================

  0  VERDE     Condición 2D geométrica razonablemente robusta
               (ángulos articulares en plano imagen, distancias normalizadas,
               alturas relativas en imagen).

  1  AMARILLO  Heurística dependiente de perspectiva / foreshortening.
               Ejemplos: ratio ancho_hombros/altura_torso ≈ frontalidad;
               cruce de línea media 2D; torsión aparente hombros–cintura.
               NO interpretar como medición 3D.

  2  ROJO      No observable de forma fiable con pose 2D.
               El programa NO inventa segmentos para estas clases.

16. QUÉ CALIBRAR CON DATOS REALES
================================================================================

Prioridad alta:
  1. Ángulos de codo (extended / flexed / straight) — varían con oclusión
     y foreshortening.
  2. Distancias muñeca–cintura / pecho / hombro (enter/exit).
  3. Duraciones mínimas y merge_gap_s según FPS real del clip.
  4. Deltas de acciones (extend_delta, approach_delta, raise_delta).

Prioridad media:
  5. Umbrales de elevación / brazo abajo / horizontal.
  6. Ventana de suavizado (smooth_window) según ruido del extractor YOLO.
  7. min_action_speed_norm_s.

Prioridad baja / solo si se usan etiquetas amarillas:
  8. Ratios frontal/perfil y twist hombros–cintura.
  9. cross_midline (cruce 2D).

Método recomendado de calibración:
  - Revisar clips con validate_realtime_full.py
  - Ajustar DetectionConfig
  - Regenerar .txt con detect_actions.py --debug
  - Comparar reasons / features CSV con lo observado


================================================================================
17. LIMITACIONES (DETALLE)
================================================================================

17.1 Limitación fundamental: NO HAY PROFUNDIDAD
-----------------------------------------------
Un esqueleto 2D es la proyección de un cuerpo 3D en el plano de la cámara.
Por tanto:

  - No se puede saber con fiabilidad si un brazo va HACIA DELANTE o HACIA ATRÁS.
  - No se puede medir el ángulo 3D real del hombro.
  - No se puede medir la profundidad real de una muñeca respecto al torso.
  - La rotación 3D exacta del torso no es observable.

Estas capacidades están explícitamente marcadas CODE=2 y NO se estiman
como si fueran fiables.

17.2 Perspectiva y foreshortening
---------------------------------
  - En vista de perfil, el ancho aparente de hombros cae → PERSON_PROFILE_HEURISTIC
    puede activarse aunque la persona no esté de perfil “perfecto”.
  - Un brazo extendido hacia la cámara parece “recogido” en 2D (ángulo de codo
    proyectado engañoso).
  - Distancias 2D normalizadas cambian con el zoom / distancia a cámara aunque
    la escala corporal mitiga parte del efecto.

17.3 Cruce de brazos / línea media (CODE=1)
-------------------------------------------
  - Que una muñeca cruce la línea media en la imagen NO implica cruce anatómico 3D.
  - En oclusiones o perfiles puede haber falsos positivos de ARMS_CROSSED.

17.4 Calidad del .npy de entrada
--------------------------------
  - NaNs, oclusiones, track switches (user_id), keypoints degenerados (puntos
    coincidentes → ángulo NaN).
  - poses_full puede tener muchos frames inválidos; valid_mask ayuda a interpretar.
  - Si el extractor YOLO falla, el detector heredará el error.

17.5 Alineación vídeo ↔ pose
----------------------------
  - Si clip.mp4 y poses_full.npy no tienen el mismo número de frames, la
    superposición en validate_realtime_full puede desfasarse en el tramo final.
  - El FPS incorrecto desplaza todos los timestamps del .txt.

17.6 Sobredetección / ruido de etiquetas
----------------------------------------
  - Muchos estados pueden estar activos a la vez (diseño intencional).
  - Heurísticas CODE=1 pueden parpadear o activarse en tramos largos.
  - Acciones dinámicas pueden fallar si el movimiento es muy lento o muy rápido
    respecto a los deltas configurados.
  - Usar --filter en las UIs para centrarse en familias de interés
    (ej: WRIST_NEAR, EXTEND_ARM).

17.7 No es un sistema de seguridad / producción sin calibrar
------------------------------------------------------------
  - Los thresholds son iniciales.
  - No hay garantías de recall/precision hasta validación con dataset anotado.
  - No sustituye supervisión humana en aplicaciones críticas.

17.8 Dependencias de entorno
----------------------------
  - Tkinter requiere display gráfico.
  - matplotlib puede ser incompatible con ciertas versiones de NumPy.
  - OpenCV necesario solo para validate_realtime_full.

================================================================================
20. NOTAS DE MANTENIMIENTO
================================================================================

- Cambiar thresholds: editar DetectionConfig en har_pose/config.py
- Cambiar orden de keypoints: editar KEYPOINTS (único sitio canónico)
- Añadir un estado nuevo: StateDetector.detect_all + (opcional) documentación aquí
- Añadir una acción nueva: ActionDetector con FSM explícita (no solo umbral estático)
- El .npy por defecto se cambia en DEFAULT_NPY_RELATIVE (config.py)
- La raíz de datos es VIDEOS_DIR = <proyecto>/videos
- La raíz de resultados es DEFAULT_OUTPUT_DIR = <proyecto>/output
